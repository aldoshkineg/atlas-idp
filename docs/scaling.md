# Autoscaling — KEDA & HPA

Scaling is driven by real signals, not just CPU: KEDA watches the Redis job queue and
scales the worker; the HPA machinery underneath is generated by KEDA on top of
metrics-server.

## Components

| Component      | App manifest                                        | Chart / version         | Namespace     | Wave |
| -------------- | --------------------------------------------------- | ----------------------- | ------------- | ---- |
| KEDA           | `gitops/platform/delivery/keda.yaml`                | `keda` 2.14.0           | `keda`        | 8    |
| metrics-server | `gitops/platform/observability/metrics-server.yaml` | `metrics-server` 3.12.2 | `kube-system` | 2    |
| Redis (broker) | `gitops/platform/storage/redis.yaml`                | bitnami `redis` 24.0.8  | `redis`       | 7    |

Redis: standalone, 256Mi PVC on `linstor-replicated`, auth via the Vault-backed
`redis-auth` secret, metrics exporter enabled.

## How the reference workload scales

The `seal-worker` consumes jobs from the Redis list `seal:jobs`. Its `ScaledObject`
(deployed from `gitops/workloads/atlasteam/seal/resources/infra/keda-scaledobject.yaml`,
generated from `templates/gold/infra/keda-scaledobject.yaml.tmpl`):

| Setting            | Value                                                             |
| ------------------ | ----------------------------------------------------------------- |
| trigger            | `redis` — `listName: seal:jobs`, `listLength: 1`                  |
| address            | `redis-master.redis.svc.cluster.local:6379`                       |
| auth               | `TriggerAuthentication` → `seal-worker-secret` (`REDIS_PASSWORD`) |
| replicas           | min **1** / max **20** (golden default: min 0 = scale-to-zero)    |
| polling / cooldown | 10s / 60s                                                         |

KEDA creates the actual `HorizontalPodAutoscaler` (`keda-hpa-<name>`) automatically —
there are no hand-authored HPAs in the repo. `metrics-server` (with
`--kubelet-insecure-tls` for the Talos lab) provides the resource-metrics API for any
plain CPU/memory HPA and `kubectl top`.

The `seal-api` is intentionally **not** autoscaled — it runs a fixed-replica Argo
Rollout with canary analysis (delivery concern, not capacity; see
[`adr/`](adr/README.md) and `apps/seal/charts/seal/templates/rollout-api.yaml`).

New workloads get the same pattern for free: `atlasctl new` scaffolds a
`ScaledObject` on `{{APP}}:jobs` — see [`workloads.md`](workloads.md).

## Real usage

```bash
make test-keda      # e2e: waits for KEDA + external metrics API, deploys a ScaledObject,
                    # forces scale 0→3, asserts readyReplicas, then scales back to 0
make test-redis     # broker health: ExternalSecret, auth (NOAUTH vs PONG), KV, Streams

kubectl get scaledobject,hpa -A            # scaling state
kubectl top pods -n atlasteam-seal         # metrics-server path
# queue-driven demo: push items to seal:jobs and watch the worker scale
kubectl -n redis exec deploy/redis-master -- redis-cli -a "$PW" lpush seal:jobs x
kubectl -n atlasteam-seal get pods -l app=seal-worker -w
```

`tests/scripts/keda-test.sh` validates the whole control loop — external metrics API
registration, operator/webhook health, CRDs, ScaledObject → HPA generation, scale-up
within 60s and scale-down — without depending on the seal workload.

## Known limitations

- Deployed seal worker keeps `minReplicaCount: 1` (warm worker); scale-to-zero is one
  line away and is the golden-template default.
- The alert `HPAMaxedOut` (see [`observability.md`](observability.md)) fires when a
  workload is pinned at `maxReplicaCount` for 15m — the capacity signal to raise limits.
